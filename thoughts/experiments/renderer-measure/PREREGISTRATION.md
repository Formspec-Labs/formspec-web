# T17 renderer comparison preregistration

Decision: Recommend the next evidence-backed renderer choice to O-17; this experiment does not select or adopt a renderer.
Hypotheses: H1 the current vendored React renderer can display and operate the same structured forms as maintained formspec-render + USWDS. H2 USWDS improves bounded automated accessibility/keyboard outcomes, without suppressing fields. H3 photo/party/edit/signing gaps primarily require shared engine or host work rather than a renderer switch. Evidence of missing controls, errors, hidden required answers or failed keyboard operations weakens H1/H2. Static APIs inform H3 but cannot prove complete journeys.
Arms: A current web vendored React/engine/layout/types and existing default CSS; B maintained sibling prebuilt webcomponent/adapters/engine/layout/types with shipped USWDS base/rules CSS. Package/version and CSS bundle are changed together: no causal attribution to renderer alone. No fresh package/WASM build is claimed.
Cases: pinned NJ form-v2 manifest and its current document filenames, claimant record; constructed DS-82 subset draft (name, citizenship, photo, attestation), explicitly not an authoritative passport form. NJ en/es and DS draft en; desktop 1280x900 and mobile viewport 390x844. Draft includes required text preceding choice for known blur/input regression. Snapshot/hash every source input. Preserve authored NJ theme; adapter identifier may be remapped to maintained uswds as documented. No bespoke question UI.
Held constant: Chromium installed by web Playwright, one worker/browser, same input JSON, localhost unused port, same generic mounting landmarks, blank starting answers, deterministic claimant record, no service calls or adoption changes. Up to 12 arm/case cells (2 arms x 3 language/form inputs x 2 viewports), one fresh page per cell; one rerun of a failed cell permitted only for harness diagnosis. Time bound 25 minutes of browser/harness execution; no package installs or broad builds.
Measures: mount outcome and console/page/request failures; axe WCAG2A/AA and WCAG21A/AA results; DOM field/control counts; keyboard focus sequence/choice operation; required-error announcement evidence; file/camera control inventory; static party/edit/signing API scope. Screenshots, requests and raw JSON retained. Desktop mobile viewport is simulation, not phone trust/camera/OS-reader evidence. Load times optionally retained as dev-server diagnostics only; no production latency/size comparison without isolated builds.
Decision rule: A mount/accessibility/keyboard blocker makes equivalence unsupported on that case. Recommend an arm only when it operates both supplied inputs with no serious/critical axe violation and no demonstrated keyboard regression; otherwise recommend further investigation with exact blockers. Unavailable signing/camera/party endpoints are capabilities not exercised, not passes and not renderer failures. Even a stronger arm remains pending O-17 and phone/VoiceOver/NVDA checks. Keep original criteria and append amendments if needed.
